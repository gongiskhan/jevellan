# Surface map

This map lists, for every capability of Jevellan, the engine service and route that owns it, the MCP tool action that reaches it, the web screen that shows it, whether decision logic still lives in that screen, and the tests that cover it. It also holds the inventory of web logic that must move into the engine, the settings fields mapped to `config` keys, the Jev question sets and prompts, and everything the engine runs on a schedule. The bridge rule behind it: the engine owns every decision, and the UI, the MCP tools, the CLI and the remote endpoint are thin clients over the same services.

The "Logic moved" column and the Phase column of the inventory say in which phase of this branch each piece of UI logic moves into the engine: overview and thread list in phase 2; jobs, nights and deploy in phase 6; goals in phase 7; Jev (decisions, overrides, corrections, why panels) in phase 8; settings and accounts screens in phase 9; everything else (devices and mesh, health checks, cleanup, thread page, task page, conversations, rigging, improver, terminals, setup) in phase 10. "no logic" means the screen only renders values the engine computes. The four-layout browser journeys (desktop 1440x900, phone 390x844, light and dark) of the rewired screens are left to the later pass; this map only records which rows need them.

Conventions: "new:" names a service or route that this branch adds (some are in progress in the working tree, for example `packages/projects/src/owner-status.ts`); every other module, route and symbol exists today and was read in the code. Route names such as `task-action` are the entries of the closed route table in `apps/daemon/src/project-work-api.ts`. Pre-existing project "bridge" code (`packages/projects/src/bridge-tools.ts`, `POST /api/bridge`) serves the coordinator's own tools and is unrelated to the twelve owner tools. The inventory is written from the code as it stands; rows pointing at a settings field that the spec's config table does not list say `proposed:`.
