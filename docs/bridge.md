# The bridge

Jevellan can be driven from Claude Code. The engine owns every decision; the web UI, the plugin's tools, the command line and the remote endpoint are clients of the same services.

## Pieces

- **Twelve tools** served by the state point at `POST /api/local/tools/:name`: `status`, `activity`, `ask_coordinator`, `work`, `goals`, `jobs`, `thread`, `respond`, `override`, `jev`, `config`, `login`. Every call is written to the caller log for 30 days.
- **The forwarder**, `jevellan mcp`: the stdio MCP server the plugin starts. It lists the tools and forwards each call. In a session Jevellan itself started (a coordinator or a thread, `JEVELLAN_ROLE` set) it lists none.
- **The plugin**, generated by `jevellan plugin build` from `plugin/` into the installation's data folder, with five slash commands (`/jevellan:status`, `/jevellan:overnight`, `/jevellan:goals`, `/jevellan:configure`, `/jevellan:jev`) and a session-start hook. `jevellan plugin install [--claude-config-dir <dir>]` installs it through a local marketplace.
- **The bridge**, `jevellan bridge [--project p] [--restart] [--stop]`: one Claude Code session per project on the state point, Sonnet at medium effort, under remote control so it shows in the Claude app as "Jevellan · {project}". It can only use the Jevellan tools. Jevellan starts it again with `--continue` when its tmux session is gone. Remote control needs an interactive Claude login in the account's folder (`bridge.account`, default `main`).
- **Push**: items waiting on the owner and Jevellan's system events reach the bridge as channel messages (`push.transport channel`), or typed into its pane while it is idle (`inject`). Quiet hours hold them and send one summary when they end; urgent ones go at once; more than three at a time arrive as one message. The bridge acks each push and receives every unacked one again when it reconnects.
- **Terminal**: `jevellan call <tool> [action] [--key value ...]`, `jevellan watch [target] [--all]`, `jevellan attach T31` for a held thread, and `jevellan statusline [--wrap '<command>']` with `jevellan statusline install`.

## Display ids

The owner says ids out loud, so every object gets a short id per project, never reused: `C` the coordinator, `T` tasks and their threads, `J` job runs, `W` waiting items, `D` decisions, `G` goals, `R` Jev rules, `L` lessons, `P` prompt proposals, `H` health checks. Every tool accepts the short id or the internal one.

## Shared thread controls

Source after 0.7.2 adds `thread actions`, which returns the same versioned action model the UI uses, and `thread act`, which accepts `operation` and a retry-stable `clientRequestId`. The eight operations are fix-checks, resolve-conflicts, address-comments, publish, land-now, land-instead, resolve and reopen. Read the model first for eligibility and consequences; a resolve with unpublished commits needs `confirm: true`. `thread merge` always requires confirmation. Execution uses the existing action receipts, publication checks and merge guards. Member work stays on its owning device through the normal authenticated owner route. These additions do not add a thirteenth tool and are not yet installed.

Jobs list/night structured data now includes the same versioned jobs projection used by Routines. Pause/Resume and nightly enablement use revision-checked patch services shared with the UI; Run now keeps its original retry receipts and refuses new work while the job or project is paused. This source remains uninstalled.

Source after 0.7.2 adds `jobs editor` and `jobs save` for the same versioned job/nightly editor models and canonical saves used by the UI. Defaults, limits and eligible choices come from the engine; saves preserve revisions, retry identity and coordinator ownership. Editor request data is available through MCP structured/text results and the CLI; remote output is redacted before serialization. These changes remain source only.

Source after 0.7.2 shares the deploy summary between the UI and `jobs deploy`. The engine supplies current/baseline/unknown state, health copy and revision-bound rollback eligibility and confirmation. A recorded baseline is labelled as such. Confirmed rollback retains canonical guards and member-coordinator ownership; it remains refused remotely. This source is not installed.

Source after0.7.2 serves shared deploy/routine settings metadata through `config routines` and the UI. Nightly and Automatic stay disabled in the UI; change mode through config. Slot edits preserve the configured mode. `config set` supports deploy jobId/desktopJobId/suiteJobId (`none` clears) and routines nightlyWindow.enabled/time/timezone and refill.enabled/minIntervalMinutes. Automation preferences use an explicit separate Save with their own revision, leaving main settings drafts intact. Jobs list/night projections reach MCP structured/text clients. These source additions are not installed.
