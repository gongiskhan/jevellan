# PJ7 - Terminal takeover

**Evidence label: simulated.** Projects phase 7 (BRIEF-projects.md section 13, local and untracked like BRIEF.md) passes PJ7 on 2026-10-05 (goncalos-macbook-pro) as one integration test that runs the real installed command against a booted daemon, beside the command and local route tests, and as one Playwright browser journey in four layouts (desktop and phone, light and dark). **The provider CLIs are simulated**, as brief section 13 asks for PJ7 ("integration with simulated provider CLIs on PATH"): the tests put simulated `claude` and `codex` executables first on a PATH of only the fixture folder and `/usr/bin:/bin`, so the owner's own CLIs are never found. **No real Claude or Codex session was resumed.** The owner's installed `claude` and `codex` ran only to print their help, with scratch home and configuration folders, to detect the flags the command passes (below). **The automated vision checks were not run** (`JEVELLAN_TEST_CLAUDE_TOKEN` is not set, ENV-CLAUDE), so every PJ7 vision record says `not run`. A builder visual review of the screenshots (below) found and fixed problems but does not stand for the vision checks. No part of this evidence is live, and Gonçalo's acceptance is not claimed.

- **Real:** the installed command (`bin/jevellan.mjs`) as its own process, with its control-file client, argument checks, environment, process group, exit codes and signal handling (SIGTERM forwarded, Ctrl-C delivered by a real pseudo-terminal); the daemon started on loopback with its installation control file, its local routes and their authorization; the thread runner, its ledgers, the hub index and the coordinator queue; Git, the project checkout and the thread's worktree; the native session files in the account home and the transcript worker that lists and reads them. In the browser journey: Playwright's Chromium driving the compiled web application against the `scripts/test-server.mjs --projects` fixture server, the daemon's own attach and detach, and the browser's Clipboard API and selection copy.
- **Simulated:** the provider CLIs (`tests/fixtures/agent-cli.mjs` behind node-shebang `claude` and `codex` executables: they record their arguments, variable names and a sha256 of the authentication variable, write a new native session in the account home as a CLI that forks the session on resume would, echo standard input and exit on `exit {code}`); the thread turns (FakeRuntime scripted turns that call the daemon's real bridge); the accounts (a shared Claude subscription account with a test secret, a per-device Codex account). In the browser the terminal itself is not involved: the fixture's control routes call the daemon's attach and detach the way the command does, so the journey proves the page's attached state and the copy paths, not the command.
- **Not run:** the vision checks (ENV-CLAUDE), a live terminal session with the real `claude` or `codex` (resuming a session the SDK created, first-run prompts in a never-interactive account home), live Jev (ENV-JEV) and PJ-live (phase 8).

## The Claude effort flag

Brief section 13 asks the command to pass Claude's effort only if the installed CLI supports an effort flag, detected with `--help`, and the result to be recorded in REPORT.md (decision 540). The command runs `claude --help` at every attach (at most 15 seconds, the account home, no authentication variable) and adds `--effort {effort}` only when the help lists `--effort`; a failed or slow probe means no flag. Codex always gets `-c model_reasoning_effort="{effort}"`.

Detected on 2026-10-05 on this machine, with scratch home and configuration folders, never the owner's homes; only the help was printed:

- `claude` 2.1.289 at `~/.local/bin/claude`, first on this machine's PATH, lists `--effort <level>` (low, medium, high, xhigh, max), `-r, --resume [value]` and `--model <model>`: attach passes `--effort`.
- An older `claude` 2.1.19 at `/opt/homebrew/bin/claude` lists no effort flag: a PATH that finds it first gets no `--effort`, which `tests/thread-attach-cli.test.ts` checks with a simulated `claude` whose help lacks the flag.
- `codex-cli` 0.154.0 has `codex resume [OPTIONS] [SESSION_ID] [PROMPT]` with `-m, --model <MODEL>` and `-c, --config <key=value>`.

## Limits

- Everything above is simulated: the provider CLIs are fixture executables, and no real Claude or Codex session was resumed in a terminal. Whether a real `claude --resume` or `codex resume` accepts a session the SDK created, and what an account home that never ran interactively asks on first use, are unverified. PJ-live (phase 8) runs the live journey or records it as blocked.
- The vision checks were not run, so no screenshot has a vision judgment. The builder review is a single pass by the builder, not the vision checks brief section 13 asks for.
- The browser journey attaches and detaches through the fixture's control routes, not through the command; the command is proven by the integration tests only. The copy fallbacks are exercised in Chromium only; iOS Safari's selection copy on the plain-HTTP Tailnet address is not run.
- Stop and Restart still act on an attached thread (brief 7.1 refuses only messages), so stopping an attached main thread settles its checkout under the owner's terminal. Attach does not hold the account's one-run-at-a-time guard, so a headless turn on the same Codex account can run beside the terminal. During the attach of a main thread, the session of a conversation working in the same checkout with the same account could be adopted (the checkout claim makes that unlikely).
- A launch failure (no executable, no folder, a start error) still sends the coordinator the owner-worked line, because detach cannot know that nothing ran. A signal during a hung attach request waits for its 45-second timeout.
- The attached session gets the minimal environment of headless turns, so COLORTERM, LC_* and SSH_AUTH_SOCK are dropped (no truecolor detection, no agent-based SSH pushes there). Standard input redirected from a file inside a terminal would get Ctrl-C twice. The pseudo-terminal Ctrl-C test runs on macOS only.
- The takeover line also shows while a turn runs, where the command answers that the thread is working: the line says how, the daemon says when (decision 543).
