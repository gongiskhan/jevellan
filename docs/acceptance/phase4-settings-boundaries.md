# Remaining Settings hub boundaries

Project saves now preserve the original submission and local context inspection in a versioned document inside the owning device's isolated home. The shared project mutation uses a transactional hub receipt. Retrying after a lost response, including after a daemon restart, uses the same project write and context request. An existing context operation is reconciled; a superseded project save cannot start new context work against later settings. The response shows the current project.

Jev key saves use the same transactional hub receipt mechanism, storing a keyed fingerprint and public summary only. A replay leaves a later key intact and returns its current summary. Submitted keys stay out of the receipt and local project-save documents.

Account-local Rigging operations now wait for account admission at the hub. File editing, parking, restoration and cancellation then use their existing local authority and stale-file checks. Promotion uses its existing durable capture request when the hub reply or subsequent delivery is unavailable. Closing a waiting local editor cancels its request instead of saving later after it has been dismissed.

Device invitation and switch-grant issuance can wait and repeat. Consuming a one-use switch token is kept separate and is not automatically retried. Checking the Jev connection is also safe to repeat after a typed hub failure. Project and context forms propagate cancellation to their waiting requests. Stopping a promotion or move also skips its follow-up inventory refresh, so cancellation cannot immediately open another wait.

Context choices now record their durable operation before any shared mutation. The previous admission path updated observed context first; losing that response advanced the project revision before the operation existed. Owned context execution already records its resulting shared state and handles hub recovery, so the extra early write has been removed.
