## Integration and pure tests

`tests/projects-placement-app.test.ts` (new, 3 tests) boots the daemon through the shared project fixture with two FakeRuntimes, a menu of `swift` (`fake`, `low` and `high`), `deep` (`fake2`, `high` and `max`) and, for PJ4b, `deep-lite` (`fake2`, `low` and `high`), one account per runtime and a saved Jev key. The scripted Jev transport answers only `placement-state-v1` packets and records every call's model, questions, packet and `Authorization` header. Each test ends with the fixture's leak check: no Jev key, GitHub token, browser session, bridge token, native session id or worktree path in any view, ledger or hub record.

- `PJ4 Jev places threads with recorded probabilities and falls back on failure`: the clauses above, plus the packet's project, thread and (for a later start) active threads with the device name, model label and effort.
- `PJ4b overrides change the next launch and restarts feed the packet`: the next-turn overrides and their coordinator summaries (`Effort changed from max to low.`, `Model changed from deep to deep-lite. Note: Lighter is enough now.`), a repeated request that changes nothing, 409 `From the next turn, the model must use the same runtime.`, 400 `From the next turn, only the model and effort can change.`, the restart (`Model changed from deep-lite to swift. Restarted as {newId}. Note: Swift is enough for this.`), a retried restart that returns the same thread, 409 `This thread was already restarted.`, the packet sentences, and 409 `This thread has an open pull request.` for a thread in review.
- `PJ4b an override during a running turn applies from the next turn, and a restart ends the running turn`: the running turn keeps `deep-model` and `max`, its own writes keep the override, the next launch takes `deep-lite-model` and `low` on the same session, and a restart of a running thread stops it with the restart reason and starts the new thread.

`tests/projects-placement.test.ts` (19 tests, 8 new in phase 4) covers Call A and Call B, resolution, the fallback for every Jev failure, a failed Call B that keeps Call A (decision 474), `main` with a model no main checkout can run (decision 478), the refusal before any call, and the packet: redaction before the task is shortened (a secret across the 6,000-character cut never leaks a prefix), the newest override sentences, and an oversized packet that drops reserved paths, then threads, then overrides, oldest first, and falls back as `state-too-large` (decision 477). Phase 4 also adds `placement asks Jev with the packet: active threads oldest first with this device's own copies, the last overrides with titles and the note; a hub outage leaves the hub part out (D249, D252)` to `tests/project-admission.test.ts` and `placement overrides are append-only, recorded by the thread owner, idempotent by id and listed newest first per project (D252)` to `tests/project-hub-store.test.ts`, and extends the schema, copy, runner, thread and API tests for the new operations, texts and route.

- The vision checks were not run at the phase gate, so no screenshot had a vision judgment then. The builder review is a single pass by the builder, not the vision checks brief section 13 asks for. - The only fully green browser matrix ran on two workers; the four-worker run had two load timeouts that passed alone. The tablet widths (761 to 1180 px) are covered only by hand checks.
