# Project request completion and transcript controls — 2026-10-07

The owner requested consecutive identical tool calls in one open area, app requests that return a usable running-app link, and direct coordinator model and effort overrides.

Tool calls now group by exact name and adjacency, including separate native assistant records. Different tools, prose, thinking, owner messages and thread reports end a group. Each call keeps its own input, output and state; streamed calls append to the same area. This renderer serves threads, ordinary conversations and runtime sessions. Thinking and the existing long-prompt treatment retain their previous behavior.

The project header offers **Override coordinator**, with the configured model menu, automatic selection and all five effort choices. Unsupported effort maps to the nearest supported effort. Saving uses the existing revision check and preserves isolation, setup and thread limits. The current turn finishes; the next turn uses the choices and starts a new native session when needed. A separate choice requests a fresh session on the next turn. Fable is not mandatory: automatic selection uses the first eligible menu entry, retaining an eligible existing session.

Jev identifies the requested result using the latest owner message and recent conversation. The versioned receipt stores the outcome, probabilities and call metadata once per event, without another copy of owner text. The coordinator receives that result and is instructed to carry it into the thread task and check the report against it. When Jev is unavailable, the receipt records that explicitly and the coordinator interprets the original request. Code does not recognize request keywords or invent launch commands.

Threads can start, list and stop managed apps. Static apps serve their HTML and assets; command apps receive an allocated port and isolated home, without inherited authentication variables. Command processes are separate from model turns; HTTP and WebSocket traffic pass through the owned listener. A tailnet app gets a separate HTTPS origin on an unused port from 9600–9699, preserving root asset paths. Publication verifies the route and response, and removal checks the recorded target before removing that route. Existing Tailscale routes remain in place. Without a tailnet origin the tool reports local access explicitly. App files must belong to the thread or its registered project checkout; the latter accommodates an untracked app absent from a worktree. Agent and runtime homes are refused.

Apps remain available after a thread reports done. Shutdown stops them. Startup recovery removes recorded routes and terminates recorded owned processes by their identities; it records them stopped rather than automatically restarting arbitrary commands. A later app request can start them again. These lifecycle choices fill specification gaps and are recorded as decisions 606–608 in REPORT.md.
